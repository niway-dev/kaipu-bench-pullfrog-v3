# ADR 0044: The UI state catalog runs on the browser harness, not Electron

## Status

Proposed — design PR pending review. [NIW2-625](https://linear.app/niway/issue/NIW2-625/ui-state-catalog-on-demand-screenshots-of-every-desktop-screen-and).
Spec: [UI state catalog — design](/specs/2026-11-04-ui-state-catalog-design/). Builds on
[0006](/architecture/decisions/0006-desktop-e2e-in-the-candidate-tier/) and
[0027](/architecture/decisions/0027-verify-release-candidates-only/) (where Electron runs), and on
[0022](/architecture/decisions/0022-screenshot-capture-native-where-the-os-has-it/) (what the
renderer does not draw). Companion:
[0045](/architecture/decisions/0045-ui-catalog-images-live-in-a-separate-repository/).

## Context

The owner wants a map of what the desktop app really looks like: one screenshot per screen and
per UI state, regenerated on demand and once per release, because the design mocks drift and
the UI changes weekly. The question is what drives the renderer to each state.

Three facts constrain the answer:

- **Electron does not run on the owner's machine.** A killed Electron leaves a macOS dialog and
  a hung main process has already cost a day (`uiohook` deadlock, 2026-10-28). The desktop
  Playwright suite runs only in the release-candidate tier in Actions (ADR 0006, ADR 0027), and
  the `verify` skill's Electron scenarios run on another machine.
- **The renderer is one HTML entry with eight render targets.** `main.tsx` picks the full app,
  the tray panel (`?mode=capture`) or one of six floating windows (`?window=…`) from the URL
  query, and every one of them talks to main only through `window.electronAPI`. The preload
  contract is a typed interface (`src/shared/types/electron-api.ts`).
- **A browser harness already exists and works.** `.evidence/harness/` (git-ignored) builds the
  renderer with Vite in production mode, with the app's StyleX plugin, swaps
  `kaipu-media://` for fixture files, installs a fake `window.electronAPI` seeded with neutral
  data, and shoots it with `playwright-core` driving system Chrome at 1440×900 @2x. It
  produced the pictures for NIW2-606, NIW2-619 and the Kaipu Black stack, and its images match
  what the owner sees in Electron for everything the renderer draws.

What the harness cannot show: native macOS UI. The screenshot selector is the system
`screencapture` binary (ADR 0022), permission prompts are TCC dialogs, folder and file pickers
and the tray menu are native. Those are flows a reader of the catalog must still know about.

## Decision

1. **The catalog's driver is the browser harness, promoted into the repository** at
   `apps/kaipu-record/ui-catalog/harness/`. It builds the real renderer (same source, same CSS)
   for plain Chrome and installs a fake preload bridge before the app loads. No Electron process
   is started by any catalog command.
2. **Every render target is in scope**: the full app on every route, the tray panel and the six
   floating windows, each loaded with the query main would use and shot at the size main gives
   it.
3. **A state is a bridge seed plus steps.** The fake bridge takes a per-state JSON seed (settings,
   auth, library, recording state, permissions, …) and a list of pushed payloads for windows
   fed by subscriptions; interaction steps are data (click, hover, press, wait) so the README
   can say how a state is reached.
4. **The bridge is typed against the preload contract.** The fake implements
   `KaipuElectronAPI`; an unmodelled member falls back to a logged no-op, never a crash, and
   the log is part of the run's output.
5. **Native UI is declared, not drawn.** The catalog has `notCapturable` entries that produce a
   README line and no image. The catalog never claims to show main's behaviour, window stacking,
   focus or anything native.
6. **The harness replaces the throwaway `harness-tmp/` of the `verify` skill** for whole-screen
   and component shots; PR evidence and catalog images come from the same build.

## Alternatives rejected

- **Playwright driving the built Electron app** (`_electron.launch`, as `e2e/` and `verify/`
  do). The real thing, including native windows. Rejected: forbidden on the owner's machine, a
  cold launch per state is slow (the E2E suite is 210 s of a 234 s run), and screen, camera and
  microphone states need OS permissions a throwaway userData does not have. It remains the only
  way to picture native behaviour, which is why `verify/` keeps its scenarios.
- **Storybook (or Ladle) with one story per state.** Mature tooling and a browsable UI.
  Rejected: a large dependency for an occasional run, and every state would be written twice,
  once as a story with mocked props and once as the real page with its hooks; the two drift,
  which is the problem the catalog exists to fix. The harness renders the real page.
- **Auto-discovery: crawl every route and click every control.** No catalog to maintain.
  Rejected: it cannot name what it finds, produces hundreds of near-duplicate frames, and a
  change in the UI changes the crawl, so two runs are not comparable.
- **Capturing the running app with the OS screenshot tool.** Native and exact. Rejected:
  needs the app to run, a person to drive it, and screen-recording permission; not reproducible.

## Consequences

- Catalog images show what the renderer draws for a given bridge state, in Chrome. Chrome and
  Electron share the engine but not the version; a rendering difference between them is possible
  and the README says so.
- Native flows have no picture. The "Not capturable" section is the only trace of them.
- The fake bridge must grow with the preload contract. A new IPC member that the renderer reads
  at load shows up as an `unmodelled` line until modelled; the typed interface makes a renamed
  member a compile error in the fake.
- `playwright-core` with system Chrome stays the browser (never `playwright install`), so the
  run is tied to a macOS machine with Google Chrome; a CI recount would render with other fonts.
- The prototype's lesson stands as a rule: the Vite build runs with cwd `apps/kaipu-record`, or
  the StyleX scanner misses the app's globs and the images lose their CSS.

## Non-goals

- Visual regression testing, pixel assertions, or a CI gate of any kind.
- Replacing the Electron E2E suite or the `verify/` scenarios.
- Shooting the Windows or Linux renderer, the light theme, or Spanish.
- A browsable catalog UI; the output is images plus a README.

## What would reopen this

- Electron becomes runnable unattended on the owner's machine without the dialog and hang
  risks (for example a reliable sandboxed launcher), and native windows matter enough to pay the
  per-state launch cost.
- A rendering difference between Chrome and Electron's Chromium misleads a design decision.
- The fake bridge becomes a second implementation of main (more than seeds and pushed payloads),
  at which point the states belong in the E2E helpers and the driver should be Electron.
